# 코드 리뷰 체크리스트 생성기

변경된 코드를 4가지 관점(버그·가독성·테스트·보안)에서 점검하여, 리뷰어가 그대로 따라갈 수 있는 체크리스트를 만든다. 목표는 "잘 짠 코드인지 판정"이 아니라, **리뷰어가 빠뜨리기 쉬운 확인 항목을 빠짐없이 끌어내는 것**이다.

## 작동 방식

### 1. 변경 범위 파악
먼저 무엇이 바뀌었는지 확인한다. diff가 주어지면 추가/삭제된 줄을, 파일이 주어지면 변경 의도를 파악한다. 변경 규모(파일 수, 줄 수)와 성격(신규 기능 / 버그 수정 / 리팩터링)을 한 줄로 요약한다. 이 요약이 있어야 이후 항목들이 변경에 맞게 좁혀진다.

### 2. 4관점으로 항목 도출
각 관점에서 "이 변경에 실제로 해당하는" 항목만 만든다. 변경과 무관한 일반론(예: 인증 코드가 없는데 보안 항목 나열)은 넣지 않는다. 노이즈가 많으면 리뷰어가 체크리스트 자체를 무시하기 때문이다.

- **버그**: 경계 조건, null/빈 값 처리, off-by-one, 예외 처리 누락, 변경이 기존 호출부에 미치는 영향
- **가독성**: 이름이 의도를 드러내는가, 함수가 한 가지 일만 하는가, 주석이 "왜"를 설명하는가(코드가 "무엇"은 이미 말함)
- **테스트**: 변경된 분기마다 테스트가 있는가, 엣지 케이스(빈 입력·최대값·실패 경로)가 커버되는가
- **보안**: 외부 입력 검증, 비밀값 하드코딩, 권한 확인, 주입(injection) 표면 — 단, 해당 변경에 보안 표면이 있을 때만

> 관점별 항목 아이디어가 더 필요하면 `references/examples.md`를 참조한다. 변경에 익숙하지 않은 도메인일 때만 로드한다.

### 3. 체크리스트 출력
아래 형식을 정확히 따른다. 각 항목은 리뷰어가 **예/아니오로 답할 수 있는 구체적 질문**으로 쓴다. "코드를 잘 작성했는가" 같은 모호한 항목은 금지한다 — 판단 기준이 없어 무의미하기 때문이다.

```markdown
## 코드 리뷰 체크리스트 — {변경 요약 한 줄}

### 🐛 버그
- [ ] {구체적 확인 질문}

### 📖 가독성
- [ ] {구체적 확인 질문}

### 🧪 테스트
- [ ] {구체적 확인 질문}

### 🔒 보안
- [ ] {구체적 확인 질문}   ← 해당 없으면 "이 변경에는 보안 표면 없음"이라고 명시
```

관점별 2~5개 항목이 적정하다. 너무 적으면 빠진 게 있고, 너무 많으면 리뷰어가 지친다.

## 항목 작성 예시

추상적 규칙보다 입력→출력 쌍이 이해가 빠르다.

**예시 1**
입력(변경): 사용자 목록을 페이지네이션하는 `getUsers(page, size)` 함수 추가
- [ ] `page`가 0 또는 음수일 때의 동작이 정의되어 있는가? (버그)
- [ ] `size` 상한이 있어 한 번에 과도한 행을 읽지 않는가? (버그/보안)
- [ ] 빈 결과(마지막 페이지 이후) 테스트가 있는가? (테스트)

**예시 2**
입력(변경): 로그인 실패 시 에러 메시지를 "비밀번호가 틀렸습니다"로 변경
- [ ] 이메일 존재 여부가 메시지로 노출되지 않는가? (보안 — 계정 열거 방지)
- [ ] 메시지 문자열이 i18n 키로 분리되었는가, 하드코딩인가? (가독성)

## 산출물 체크리스트
- [ ] 변경 요약 한 줄을 맨 위에 포함했다
- [ ] 4관점을 모두 다뤘다 (해당 없으면 "해당 없음"을 명시)
- [ ] 모든 항목이 예/아니오로 답할 수 있는 구체적 질문이다
- [ ] 변경과 무관한 일반론 항목을 넣지 않았다

## 테스트 시나리오
- **정상 흐름**: "이 diff 리뷰 체크리스트 만들어줘" + 30줄짜리 함수 추가 diff → 4관점 체크리스트 생성, 보안 표면 없으면 명시.
- **에러 흐름**: 변경 내용 없이 "코드 리뷰해줘"만 입력 → 어떤 변경/파일/diff를 볼지 먼저 되묻는다 (빈 입력에 임의 체크리스트를 만들지 않는다).
