## 1. 왜 순차인가

Claude Code의 에이전트 팀은 **세션당 한 팀만 활성화**된다. 팀원은 독립 Claude 인스턴스이고, 팀원이 또 팀을 만들 수 없다(중첩 불가). 따라서 "다중 팀"은 여러 팀이 동시에 도는 것이 아니라, **한 팀을 만들어 일을 끝내고 정리한 뒤 다음 팀을 만드는 순차 재구성**이다.

이 제약은 약점이 아니라 설계 원리다. 순차이기 때문에 **스테이지 경계가 명확**해지고, 그 경계에 계약과 검증 게이트를 둘 수 있다. 병렬 팀이었다면 핸드오프 시점이 모호해진다.

**황금 규칙:** 다음 팀을 `TeamCreate`하기 전에 현재 팀을 반드시 `TeamDelete`한다. 정리하지 않으면 1팀 제약에 막혀 다음 팀 생성이 실패한다.

## 2. 스테이지 분해 기준

작업을 스테이지(=팀)로 나눌지 판단하는 기준. harness의 "에이전트 분리 기준"을 팀 레벨로 올린 것이다.

| 기준 | 스테이지로 분리 | 한 스테이지로 통합 |
|------|----------------|-------------------|
| 전문성 | 팀 전체의 전문 영역이 다름 (조사팀 vs 빌드팀) | 같은 영역의 세부 작업 |
| 산출물 경계 | 중간 산출물이 명확히 정의됨 (설계서, 코드) | 산출물이 뒤섞여 분리 불가 |
| 컨텍스트 | 한 팀이 다 들고 있기엔 컨텍스트가 큼 | 가벼워서 한 팀이 처리 가능 |
| 도구 | 스테이지마다 다른 도구/MCP가 필요 | 같은 도구로 충분 |

**선형을 기본으로 한다(S1→S2→S3).** 분기(한 스테이지가 둘로 갈라짐)나 병합(둘이 하나로 모임)은 계약을 N개로 늘리고 게이트를 복잡하게 만든다. 꼭 필요할 때만 쓰고, 가능하면 선형으로 평탄화한다.

**과분해 경고:** 스테이지가 많을수록 팀 생성/정리 오버헤드와 계약 관리 비용이 커진다. 2~4 스테이지가 현실적이다. 스테이지 간 차이가 모호하면 합치고, 단일 팀으로 충분하면 harness를 쓴다.

## 3. 스테이지 루프

메타-오케스트레이터가 기술하는 핵심 로직. harness 오케스트레이터 템플릿 A(한 팀 조율)를 스테이지 루프로 감싼 것이다.

```
입력: 스테이지 목록 [S1, S2, ..., Sn], 계약 목록
준비: _workspace/, _workspace/contracts/, _workspace/handoff_log.md 확인

각 스테이지 Sn에 대해 순서대로:

  1. (게이트-IN) n > 1 이면:
       contracts/{S(n-1)}__to__{Sn}.md 의 검증 체크리스트 실행
       위반 → 이전 스테이지 S(n-1)를 부분 재실행하여 계약 충족 후 진행

  2. TeamCreate(
       team_name: "{Sn}-team",
       members: [ { name, agent_type, model: "opus", prompt }, ... ]
     )

  2.5 (preflight) ── 이 스테이지에 MCP 의존 에이전트가 있을 때만 실행 ──
       MCP 사용 팀원에게 프로브 호출(예: mcp__figma__get_me) 1회를 먼저 시켜
       해당 툴 접근 가능 여부를 확인한다.
       실패 → 에스컬레이션 사다리(재시도 → 리더 격리 호출 → 계약 게이트 차단).
       (MCP 의존 에이전트가 없는 스테이지는 이 단계를 건너뛴다.)
       상세: mcp-integration-guide.md §5 참조.

  3. TaskCreate(tasks: [...])
       각 팀원 프롬프트에 "입력 계약 파일을 Read하라" 명시
       → 팀원이 contracts/{S(n-1)}__to__{Sn}.md 와 이전 산출물을 읽음

  4. 팀원 자체 조율 (SendMessage / 공유 작업 목록)
       → 산출물을 계약 produces.path 에 저장 (예: _workspace/stage0N_{name}/output.json)

  5. (게이트-OUT) contracts/{Sn}__to__{S(n+1)}.md 의 출력 스키마 충족 검증
       위반 → Sn 1회 재실행, 재실패 시 보고 후 중단

  6. TeamDelete   ← 다음 팀 생성 전 필수

  7. handoff_log.md 에 append:
       "| {날짜} | {Sn} 완료 | 계약 {contract_id} v{X} 충족 | {산출물 경로} |"

최종:
  마지막 스테이지 산출물을 사용자 지정 경로로 출력
  _workspace/ 는 보존 (사후 검증·감사 추적용)
```

`handoff_log.md`는 재개의 핵심이다. Phase 0에서 이 로그를 읽어 마지막 완료 스테이지를 알아내고, 그 다음부터 재개한다.

## 4. 데이터 흐름

**스테이지 간 데이터는 오직 파일 + 계약으로만 흐른다.** SendMessage·TaskCreate는 한 팀 내부에서만 작동하고 팀 경계(= 스테이지 경계)를 넘지 못한다.

```
[S1 팀]                          [S2 팀]
 팀원 ←SendMessage→ 팀원          팀원 ←SendMessage→ 팀원
   │ (팀 내부 통신)                  │ (팀 내부 통신)
   ↓                                ↑ Read
 _workspace/stage01_*/output.json ─┘
   │                                ↑
   └── contracts/S1__to__S2.md ─────┘  (계약이 둘을 잇는다)
```

**디렉터리 규칙:**
- `_workspace/stage0N_{teamOrAgent}/` — 스테이지별 산출물
- `_workspace/contracts/` — 계약 파일들
- `_workspace/handoff_log.md` — 스테이지 완료 로그(재개용)

최종 산출물만 사용자 경로로 내보내고, 중간 파일은 모두 `_workspace/`에 보존한다.

## 5. 에러 핸들링

| 상황 | 전략 |
|------|------|
| 게이트-OUT 계약 위반 | 해당 스테이지 1회 재실행. 재실패 시 보고 후 **중단**(깨진 입력을 다음 팀에 전파하지 않는다) |
| 게이트-IN 계약 위반 | 이전 스테이지를 부분 재실행하여 입력 충족 후 진행 |
| `TeamDelete` 누락 감지 | 활성 팀을 정리한 뒤 `TeamCreate` 재시도 |
| MCP 접근 불가 (preflight 실패) | 재시도 → 리더 격리 호출 → 그래도 불가 시 계약 필수/선택 분기. 상세: `mcp-integration-guide.md` §5 |
| 중간 스테이지 실패 | `handoff_log.md` 기준으로 완료분 보존, 실패 스테이지부터 부분 재개 |
| 팀원 과반 실패 | 사용자에게 알리고 진행 여부 확인 |

**원칙:** 파이프라인에서 가장 위험한 것은 **깨진 산출물이 다음 스테이지로 전파되는 것**이다. 한 스테이지의 오류는 그 경계에서 막아야 비용이 작다. 그래서 게이트는 "통과 못 하면 멈춘다"를 기본으로 한다.
