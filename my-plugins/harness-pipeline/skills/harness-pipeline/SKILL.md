# Harness Pipeline — 다중 팀 파이프라인 아키텍트

여러 에이전트 팀을 **순차로** 구성하고, 한 팀의 산출물을 다음 팀이 입력으로 받아 이어가는 **팀→팀 파이프라인**을 설계하는 메타 스킬.

**harness와의 관계:** harness가 "팀 빌더"(한 팀을 만든다)라면, harness-pipeline은 "팀 시퀀서"(여러 팀을 잇는다)다. **각 스테이지 = harness 1회 실행**이며, 이 스킬은 "여러 스테이지를 어떤 순서·계약으로 잇는가"만 정의하고 스테이지 내부 설계(에이전트·스킬 생성)는 harness에 위임한다.

**핵심 원칙:**
1. **스테이지 = 팀 1개.** 작업을 팀 단위 스테이지로 분해하고, 스테이지를 순차로 연결한다.
2. **계약 우선(contract-first).** 팀을 만들기 전에 인접 스테이지 간 입출력 계약을 먼저 확정한다.
3. **파일로만 핸드오프한다.** 스테이지 간 데이터는 `_workspace/` 파일과 계약으로만 전달한다.
4. **파이프라인은 진화한다.** 매 실행 후 계약·스테이지를 갱신하고 변경 이력을 기록한다.

## 반드시 지키는 제약

이 제약들이 전체 설계를 규정하므로 먼저 이해한다:

- **세션당 한 팀만 활성화된다.** 다음 팀을 만들기 전에 현재 팀을 반드시 `TeamDelete`로 정리한다. 중첩 팀(팀원이 팀 생성)은 불가하다. → 그래서 '다중 팀'은 동시 병렬이 아니라 **순차 재구성**이다.
- **팀 통신(SendMessage·TaskCreate)은 팀 경계를 넘지 못한다.** 각 팀은 독립 세션이므로, 스테이지 간 데이터는 오직 파일(`_workspace/`) + 계약(`_workspace/contracts/`)으로만 흐른다. 이를 어기면 데이터 흐름이 끊긴다.
- 모든 에이전트는 `model: "opus"`를 사용한다.
- `.claude/commands/`는 생성하지 않는다.

## 워크플로우

### Phase 0: 현황 감사

파이프라인 스킬이 트리거되면 가장 먼저 기존 진행 상황을 확인한다.

1. `_workspace/contracts/`, `_workspace/handoff_log.md`, `_workspace/stage*/`를 읽는다.
2. 현황에 따라 분기한다:
   - **신규 구축**: `_workspace/`가 없거나 비어있음 → Phase 1부터 전체 실행.
   - **부분 재실행**: 특정 스테이지/계약만 수정 요청 → 해당 스테이지부터 재개(이전 산출물은 보존).
   - **중단 재개**: `handoff_log.md`에 마지막 완료 스테이지가 기록됨 → 그 **다음 스테이지부터 재개**.
3. 감사 결과(완료 스테이지, 활성 계약 버전)를 사용자에게 요약 보고하고 실행 계획을 확인받는다.

### Phase 1: 파이프라인 설계

1. 사용자 요청에서 전체 목표와 최종 산출물을 파악한다.
2. 작업을 **스테이지(=팀)** 로 분해한다. 각 스테이지에 대해 정의한다:
   - 책임(이 팀이 무엇을 끝내는가)
   - 필요한 전문가 조합(harness 6패턴 중 무엇으로 팀을 구성할지)
   - 산출물(다음 스테이지에 넘길 것)
3. 스테이지 간 의존 그래프를 그린다. **선형(S1→S2→S3)을 기본으로 한다** — 분기/병합은 핸드오프와 계약을 복잡하게 만들기 때문이다.
4. **과분해 방지 게이트:** "정말 여러 팀이 필요한가, 단일 harness 팀으로 충분한가"를 자문한다. 스테이지 간 전문성·컨텍스트가 확연히 다르고 중간 산출물이 명확할 때만 다중 팀으로 간다. 그렇지 않으면 harness 단일 팀을 권하고 종료한다.

> 스테이지 분해 기준과 선형/분기 트레이드오프는 `references/stage-handoff-guide.md` 참조.

### Phase 2: 계약 정의 (핵심)

팀을 만들기 **전에**, 인접한 모든 스테이지 쌍에 대해 계약을 먼저 작성한다. 계약은 한 스테이지의 출력 양식(output schema)과 다음 스테이지의 입력 양식(input schema)을 잇는 약속이다.

- 계약 파일 위치: `_workspace/contracts/{from-stage}__to__{to-stage}.md`
- 계약에는 **출력 스키마 / 입력 스키마 / 의미 계약 / 검증 체크리스트 / 버전**을 담는다.
- 입력 스키마는 출력 스키마의 부분집합이어야 한다(다음 팀이 필요한 만큼만 받는다).

계약을 먼저 확정하는 이유: 팀을 만든 뒤 양식을 맞추면 재작업이 크다. 계약이 먼저 있으면 각 팀이 "무엇을 내야 하고 무엇을 받는지"를 처음부터 알고 작업한다.

> 계약 포맷(frontmatter + 본문), semver 규칙, 검증법은 `references/artifact-contract-guide.md` 참조.

### Phase 3: 스테이지별 팀 빌드

각 스테이지에 대해 harness의 팀 설계(Phase 2 아키텍처 선택, Phase 3 에이전트 정의, Phase 4 스킬 생성)를 **1회씩** 적용한다. 이 스킬은 그 과정을 반복 호출할 뿐, 내부 설계는 harness 규칙을 그대로 따른다.

- 각 팀의 에이전트 입출력 프로토콜을 **해당 스테이지의 계약과 일치**시킨다(산출물 경로 = 계약 produces.path).
- 외부 툴(Figma 등)이 필요한 에이전트에는 `## MCP 도구 의존성` 섹션을 추가한다.

> MCP 서버 등록과 에이전트 의존성 선언은 `references/mcp-integration-guide.md` 참조.

### Phase 4: 파이프라인 오케스트레이션 (핵심)

메타-오케스트레이터 스킬을 1개 생성한다. 이것은 harness 오케스트레이터(한 팀 조율)와 달리 **여러 팀을 순차로 잇는 스테이지 루프**를 정의한다:

```
각 스테이지 Sn에 대해:
  1. (게이트-IN) n>1이면 직전 계약을 검증한다 — 위반 시 이전 스테이지 부분 재실행
  2. TeamCreate("{Sn}-team", members[... model:"opus"])
  3. TaskCreate(...) — 팀원이 계약 파일을 Read하여 입력 계약을 인지
  4. 팀원 자체 조율 → 산출물을 계약 produces.path에 저장
  5. (게이트-OUT) Sn 출력 계약을 검증
  6. TeamDelete  ← 다음 팀 생성 전 반드시 (세션당 1팀 제약)
  7. handoff_log.md에 "Sn 완료, 계약 vX 충족" 기록(append)
최종: 마지막 스테이지 산출물을 사용자 경로로 출력, _workspace/는 보존
```

> 스테이지 루프 전문, 데이터 흐름, 에러 핸들링은 `references/stage-handoff-guide.md` 참조.

### Phase 5: 계약 검증 & 핸드오프 게이트

스테이지 경계마다 계약 위반을 검증한다. 핵심은 "파일이 존재하는가"가 아니라 **"producer가 실제로 쓴 파일의 shape이 consumer가 기대하는 입력 스키마와 맞는가"** 의 경계면 교차 비교다.

- 게이트-OUT: 스테이지가 산출물을 낸 직후, 출력 계약 충족 여부 검증.
- 게이트-IN: 다음 스테이지 시작 전, 입력 계약 충족 여부 재확인.
- 위반 시: 게이트를 차단하고 깨진 입력을 다음 팀에 전파하지 않는다. 1회 재실행 후에도 실패하면 보고하고 중단한다.

> 경계면 교차 비교 방법론은 harness `references/qa-agent-guide.md`를 차용한다. 상세는 `references/artifact-contract-guide.md`의 "검증" 절 참조.

### Phase 6: 검증 & 진화

1. **드라이런:** 스테이지 간 dead link가 없는지(모든 produces.path가 다음 consumes.path와 매칭), Phase 순서가 1팀 제약과 모순 없는지(모든 팀 전환에 `TeamDelete` 선행) 확인한다.
2. **트리거 검증:** should-trigger / should-NOT-trigger 프롬프트로 오케스트레이터 description을 점검한다.
3. **CLAUDE.md 등록:** 파이프라인 포인터(트리거 규칙)와 **스테이지·계약 변경 이력**을 기록한다.
4. **진화:** 실행 후 피드백을 받아 계약·스테이지·MCP 의존성을 갱신하고 변경 이력에 남긴다.

## 산출물 체크리스트
- [ ] 스테이지 분해 완료 (각 스테이지 = 팀 1개, 선형 의존)
- [ ] 인접 스테이지마다 계약 파일 작성 (`_workspace/contracts/`)
- [ ] 각 팀 에이전트 입출력이 계약 경로와 일치
- [ ] MCP 사용 에이전트에 `## MCP 도구 의존성` 섹션 포함
- [ ] 메타-오케스트레이터에 스테이지 루프 + 게이트 IN/OUT 명시
- [ ] 모든 팀 전환에 `TeamDelete` 선행 (1팀 제약)
- [ ] 모든 Agent 호출에 `model: "opus"`
- [ ] `.claude/commands/` 생성 안 함
- [ ] 오케스트레이터 description에 후속 작업 키워드 포함
- [ ] CLAUDE.md에 파이프라인 포인터 + 계약/스테이지 변경 이력
