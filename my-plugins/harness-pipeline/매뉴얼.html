1 이게 도대체 뭔가요?

harness-pipeline은 여러 개의 "AI 작업 팀"을 정해진 순서대로 이어 붙여, 하나의 큰 일을 처음부터 끝까지 자동으로 끝내게 해주는 도구입니다.

공장 컨베이어 벨트를 떠올려 보세요.
자동차 공장에서는 한 사람이 차 한 대를 통째로 만들지 않습니다. ① 설계 팀이 도면을 그리고 → ② 조립 팀이 도면을 받아 차체를 만들고 → ③ 검수 팀이 완성차를 점검합니다. 각 팀은 앞 팀의 결과물을 받아서 자기 일을 하고, 다음 팀에게 넘깁니다.

harness-pipeline이 하는 일이 바로 이겁니다. 다만 "팀원"이 사람이 아니라 AI(Claude)일 뿐이죠.
① 리서치 팀
자료를 조사한다
→결과 전달
② 디자인 팀
조사결과로 설계한다
→결과 전달
③ 빌드 팀
설계대로 만든다
한 줄 요약: "혼자 다 하기엔 너무 큰 일"을 여러 전문 팀으로 쪼개서 차례차례 바통을 넘기며 끝내는 자동화 도구입니다.

그럼 이건 "프로그램"인가요?

아니요. 정확히는 Claude에게 "이렇게 일하라"고 가르치는 설명서(스킬)입니다. 버튼을 누르면 실행되는 앱이 아니라, 여러분이 Claude에게 부탁하면 Claude가 이 설명서를 펼쳐 보고 그 방식대로 팀을 꾸려 일하는 구조예요. 그래서 "메타 스킬"(스킬을 만드는 스킬)이라고 부릅니다.

2 5분 만에 끝내는 핵심 용어

딱 5개만 알면 나머지가 다 이해됩니다.

① 에이전트 (Agent)

일하는 AI 한 명. "조사 담당", "코드 작성 담당"처럼 한 가지 역할을 맡습니다.

직원 한 명. 회사로 치면 신입사원 하나하나입니다.

② 팀 (Team) = 스테이지 (Stage)

같은 목표를 가진 에이전트 여러 명의 묶음. harness-pipeline에서는 "팀 1개 = 작업 단계(스테이지) 1개"로 봅니다.

부서 하나. "디자인 팀", "개발 팀"처럼요. 컨베이어 벨트의 한 칸이라고 보면 됩니다.

③ 계약 (Contract) — 가장 중요!

앞 팀이 "이런 모양으로 결과를 주겠다"고, 뒤 팀이 "이런 모양으로 받겠다"고 미리 정해두는 약속 문서입니다.

식당 주문서. 손님(뒤 팀)이 "아메리카노, 샷 추가, 얼음 적게"라고 적으면, 바리스타(앞 팀)는 정확히 그대로 만들어 줍니다. 주문서가 없으면? 손님은 차를 시켰는데 커피가 나오는 사고가 납니다. 계약은 팀끼리의 주문서예요.

④ 핸드오프 (Handoff)

한 팀이 일을 끝내고 결과물을 다음 팀에게 넘기는 행위.

릴레이 경주의 바통 터치. 바통(결과 파일)을 떨어뜨리면 경주가 끝나버리므로, 넘기는 순간이 가장 중요합니다.

⑤ MCP (외부 도구 연결)

Claude가 Figma, GitHub, 데이터베이스 같은 바깥 프로그램을 직접 다룰 수 있게 해주는 연결 통로입니다. (선택 기능)

콘센트(멀티탭). AI라는 본체에 "Figma 플러그", "GitHub 플러그"를 꽂아 외부 도구의 전기를 끌어 씁니다.

3 harness vs harness-pipeline

이름이 비슷한 두 도구가 있습니다. 헷갈리지 않게 한 번에 정리할게요.

harnessharness-pipeline (이 도구)
역할팀 한 개를 잘 만든다여러 팀을 순서대로 잇는다
비유부서 하나를 꾸리는 팀장여러 부서를 줄 세우는 공장장
언제 쓰나한 팀으로 끝나는 일전문성이 완전히 다른 팀이 여럿 필요한 일
관계: harness-pipeline의 한 칸(스테이지)을 만들 때 harness를 한 번씩 사용합니다. 즉 harness-pipeline은 harness를 부품처럼 가져다 씁니다. 그래서 harness가 먼저 설치돼 있어야 합니다.
단일 팀으로 충분한 작은 일이라면 굳이 harness-pipeline을 쓰지 마세요. 팀을 여러 개 만드는 건 그만큼 시간과 비용이 더 듭니다. "전문 분야가 확연히 다른 단계가 2~4개"일 때가 딱 맞습니다.

4 어떻게 동작하나요?

Claude가 내부적으로 밟는 순서입니다. 여러분이 외울 필요는 없지만, 알아두면 "지금 뭘 하는 중인지" 보입니다.

  1. 현황 확인 — 이전에 하던 작업이 있는지 먼저 살핍니다. 있으면 끊긴 데서 이어서 합니다.
  2. 단계 나누기 — 큰 일을 팀 단위 단계(스테이지)로 쪼갭니다. 보통 2~4개.
  3. 계약 먼저 작성 — 팀을 만들기 전에 팀 사이의 "주문서(계약)"부터 정합니다.
  4. 한 팀씩 일 시키기 — 첫 팀을 만들어 일을 끝내고, 정리한 뒤 다음 팀을 만듭니다.
  5. 경계에서 검사(게이트) — 팀이 넘기는 결과가 계약(주문서)대로인지 확인합니다. 어긋나면 막습니다.
  6. 최종 결과 전달 + 기록 — 마지막 결과물을 여러분에게 주고, 작업 이력을 남깁니다.
핵심은 "한 작업대에서 한 팀만 일한다"는 점입니다. 작업대가 하나뿐이라, 다음 팀이 오려면 먼저 온 팀이 자리를 비워줘야 합니다(이걸 TeamDelete라고 합니다). 그래서 "동시에 여러 팀"이 아니라 "차례차례 한 팀씩" 입니다.

왜 데이터를 꼭 "파일"로 넘기나요?

팀끼리는 직접 대화(메신저)를 할 수 없습니다. 각 팀은 서로 다른 방에서 일하기 때문이에요. 그래서 결과를 파일로 적어서 공용 사물함(_workspace 폴더)에 넣어두면, 다음 팀이 그 파일을 꺼내 읽습니다. 이게 유일하고 확실한 전달 방법입니다.

5 설치하기 (준비물)

시작 전에 3가지가 필요합니다.

  1. harness 플러그인 먼저 설치 — 이게 없으면 harness-pipeline은 동작하지 않습니다. (각 단계를 harness로 만들기 때문)
  2. 에이전트 팀 기능 켜기 — 아래 명령으로 실험 기능을 활성화합니다.
  3. (선택) 외부 도구 쓸 거면 — Figma·GitHub 같은 MCP 서버를 설정 파일에 등록합니다.

플러그인 설치

claude plugin marketplace add jteamjang87120591-collab/harness-multi-pipline
claude plugin install harness-pipeline@harness-pipeline-marketplace

에이전트 팀 기능 켜기

Windows (PowerShell) — 지금 쓰시는 환경입니다:

$env:CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS = "1"

macOS / Linux:

export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
위 명령은 그 터미널 창에서만 적용됩니다. 매번 켜기 귀찮다면 Windows는 PowerShell 프로필($PROFILE)이나 시스템 환경 변수에, macOS/Linux는 ~/.zshrc·~/.bashrc에 추가해 영구 적용하세요.
실험적 기능 안내: 이 플러그인은 아직 실험 단계인 "에이전트 팀" 기능에 기댑니다. Claude Code 버전·환경에 따라 동작이 달라질 수 있으니, 팀에 본격 도입하기 전에 한 명이 먼저 테스트해 보길 권합니다.

6 사용하기 (말만 걸면 됩니다)

복잡한 명령어는 없습니다. Claude에게 평소 말하듯 부탁하면, Claude가 알아서 이 스킬을 펼칩니다.

이렇게 말하면 켜집니다

💬 "다중 팀 파이프라인 설계해줘 — 리서치 → 디자인 → 빌드를 팀마다 넘기는 흐름"

💬 "Figma 디자인을 받아 스펙 추출하고 코드까지 만드는 파이프라인 하네스 구성해줘"

💬 "스테이지로 나눠서 팀마다 작업 넘겨줘"

나중에 이어서 부탁할 때도 같은 스킬을 씁니다

한 번 만든 파이프라인은 다음과 같이 이어서 다룰 수 있습니다:

  • "파이프라인 다시 실행해줘"
  • "2번 디자인 단계만 다시 해줘"
  • "계약을 이렇게 바꿔줘 / 단계를 하나 더 추가해줘"
중간에 멈췄어도 걱정 없습니다. Claude가 작업 기록(handoff_log)을 보고 끊긴 단계부터 이어서 진행합니다.

이럴 땐 쓰지 마세요

아님 한 팀이면 충분한 작은 일 → harness를 쓰세요.
아님 "이 코드 설명해줘", "이거 실행해줘" 같은 단순 요청 → 그냥 일반 대화로 충분합니다.

7 실제 예시 — 디자인에서 코드까지

"Figma 디자인을 받아 → 조사하고 → 설계 스펙을 뽑고 → 화면 코드까지 만드는" 3단계 파이프라인을 따라가 봅니다.

단계팀하는 일넘기는 결과물외부도구
① 리서치조사 3명사용자 불편(페인포인트) 조사findings.json—
② 디자인추출·작성 2명Figma에서 디자인 값 뽑아 설계서 작성design_spec.json✅ Figma
③ 빌드개발·검수 2명설계서대로 화면 코드 제작src/ 코드—
① 리서치
findings.json
→계약1
② 디자인
design_spec.json
→계약2
③ 빌드
완성 코드

각 화살표 위의 "계약"이 바로 팀 사이의 주문서입니다. 예를 들어 ①→② 계약에는 "리서치 팀은 topic(주제)과 pain_points(불편 목록)를 꼭 담아 준다"고 적혀 있습니다. 디자인 팀은 그걸 믿고 받아 일을 시작하죠.

안전장치가 동작하는 순간: 만약 ② 디자인 단계에서 Figma 연결이 실패해 디자인 값(layout_tokens)이 비어버리면, ②→③ 검사(게이트)에서 걸러내고 멈춥니다. 망가진 설계서를 ③ 빌드 팀에 넘겨 엉뚱한 코드를 만드는 사고를 막는 거죠. (가짜 값으로 대충 채우고 진행하지 않습니다.)
📄 계약 파일이 실제로 어떻게 생겼는지 보기 (호기심 있는 분만)

계약은 위쪽 "기계가 읽는 부분"과 아래쪽 "사람이 읽는 부분"으로 나뉩니다.

---
contract_id: 01-research__to__02-design
version: 1.0.0
produces:
  - path: _workspace/stage01_research/findings.json
    format: json
consumes:
  - path: _workspace/stage01_research/findings.json
    required: true
---
# 계약: 01-research → 02-design (v1.0.0)

## 출력 스키마 (앞 팀이 보장)
| 필드        | 타입          | 필수 | 설명             |
|------------|---------------|:---:|------------------|
| topic      | string        | ✅  | 조사 주제        |
| pain_points| array<string> | ✅  | 불편 목록(중요도순)|

## 의미 계약
- pain_points 는 비어 있으면 안 됨 (최소 1개), 중요도 내림차순.

→ "주문서에 무엇을, 어떤 모양으로, 어떤 의미로 담을지"를 사람도 AI도 읽을 수 있게 적어둔 것입니다.

8 꼭 지켜지는 안전 규칙

Claude가 항상 지키도록 설계된 규칙들입니다. 알아두면 결과를 신뢰할 수 있습니다.

🔁 한 번에 한 팀만

작업대가 하나라, 다음 팀을 만들기 전에 반드시 이전 팀을 정리합니다. 그래서 "순서대로" 진행됩니다.

📁 전달은 오직 파일로

팀끼리 직접 대화하지 않고, 공용 폴더의 파일로만 결과를 주고받습니다. 흐름이 또렷해집니다.

🚦 경계마다 검사

결과가 계약(주문서)대로인지 확인하고, 어긋나면 다음 팀으로 못 넘기게 막습니다.

🛑 망가진 건 전파 금지

한 번 고쳐 보고도 안 되면 멈추고 보고합니다. 잘못된 결과를 끝까지 끌고 가지 않습니다.

왜 이렇게까지? 파이프라인에서 가장 위험한 건 "앞 단계의 작은 오류가 뒤로 갈수록 눈덩이처럼 커지는 것"입니다. 그래서 오류는 생긴 자리에서 바로 막는 게 가장 쌉니다.

9 자주 묻는 질문

Q. 프로그래밍을 몰라도 쓸 수 있나요?

네. Claude에게 한국어로 부탁만 하면 됩니다. 다만 설치 단계(터미널 명령 몇 줄)는 한 번 필요하고, 외부 도구(MCP) 연동은 약간의 설정이 필요합니다. 설치만 도움받으면 그 뒤로는 대화로 충분합니다.

Q. "팀이 동시에 일하면 더 빠르지 않나요?"

그게 자연스러운 생각이지만, 현재 Claude Code는 한 번에 한 팀만 활성화됩니다(작업대가 하나). 그래서 이 도구는 순서대로 진행합니다. 대신 그 덕분에 단계 경계가 또렷해져 검사·재실행이 쉬워지는 장점이 있습니다.

Q. 중간에 멈추면 처음부터 다시 해야 하나요?

아니요. 완료된 단계는 보존되고, 작업 기록을 보고 멈춘 단계부터 이어서 합니다. "이어서 해줘"라고 하면 됩니다.

Q. Figma 토큰 같은 비밀번호는 어디에 적나요?

설정 파일에 직접 적지 마세요. 반드시 환경 변수(예: ${FIGMA_TOKEN})로 참조하고, 실제 값은 별도 보관합니다. 비밀값이 깃(코드 저장소)에 올라가면 유출됩니다.

Q. GitHub·데이터베이스도 연결할 수 있나요?

네, 같은 방식(MCP)으로 연결합니다. 단, 읽기만 하는 Figma와 달리 GitHub·DB는 "쓰기·삭제"가 가능하므로 위험합니다. 조사용이라면 읽기 권한만 주고, DB는 읽기 전용 계정을 쓰는 게 정석입니다. DELETE/DROP은 한 줄로 되돌릴 수 없으니까요.

Q. 단계는 몇 개가 적당한가요?

2~4개가 현실적입니다. 너무 잘게 쪼개면 팀을 만들고 정리하는 비용과 계약 관리가 오히려 부담이 됩니다. 단계 간 차이가 모호하면 합치세요.
